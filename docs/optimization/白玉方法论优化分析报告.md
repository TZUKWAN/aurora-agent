# Aurora Agent 基于白玉方法论的优化分析报告

## 一、现状诊断

### 1.1 Aurora已具备的能力

| 模块 | 能力 | 成熟度 |
|------|------|--------|
| 工具系统 | 40+工具，14个工具文件，覆盖竞赛/BP/评估/答辩/团队/大创 | 高 |
| Hook系统 | 16种事件，Guardrails/Security/Recovery/Learning接入 | 高 |
| Swarm多智能体 | 7个专家角色，并行执行，结果合成 | 中（有缺陷） |
| 记忆系统 | SQLite持久化，分类记忆，上下文注入 | 中 |
| 评估引擎 | LLM+关键词双路径，12个评分维度 | 中 |
| BP生成器 | 10章节标准模板，LLM生成+静态回退 | 中 |
| 答辩系统 | 9类45道题，5维评分标准 | 中 |
| 竞赛数据库 | 8个竞赛，赛道/时间线/要求/权重 | 低（硬编码） |
| 接口层 | CLI/TUI/Web/MCP四接口 | 高 |

### 1.2 核心问题清单

| 优先级 | 问题 | 影响 |
|--------|------|------|
| P0 | Agent Loop不支持多轮工具调用 | LLM无法链式调用工具（如搜索→生成→评估），Agent能力受限 |
| P0 | Swarm任务分配用字符串包含匹配 | 经常分配失败，fallback到单角色，多智能体形同虚设 |
| P0 | 系统提示词缺少白玉方法论 | 没有编码"三维逻辑"等核心竞赛方法论，知识深度不足 |
| P1 | ContextCompressor未连接LLM | 只能做截断式压缩，摘要能力浪费 |
| P1 | 竞赛知识全部硬编码 | 无法更新赛规，无法适配年度变化 |
| P1 | 评估维度与白玉方法论脱节 | 评分维度是通用框架，不是竞赛评审专家的真实视角 |
| P2 | Loop工具全部空壳 | 自主循环能力无法通过工具触发 |
| P2 | SwarmBus未使用 | 角色间无通信，无法协作 |

## 三、智能体设计优化

### 3.1 修复Agent Loop（P0）

**当前问题**：`_call_llm()` 收到 tool_calls 后执行一次，然后 `_synthesize_tool_response()` 直接返回文本。LLM无法链式调用工具。

**修复方案**：在 `_call_llm()` 中实现 ReAct 循环：

```python
async def _call_llm(self, messages, tools=None, tool_dispatch=None, max_rounds=10):
    """Call LLM with multi-round tool calling support."""
    for round_idx in range(max_rounds):
        response = await self.client.chat.completions.create(
            model=self.model_name,
            messages=messages,
            tools=tools,
            tool_choice="auto" if tools else None,
            max_tokens=4096,
            temperature=0.7,
        )
        message = response.choices[0].message

        if not message.tool_calls:
            return self._extract_content(message)

        # Execute tool calls
        tool_results = self._execute_tool_calls(
            message, tool_dispatch or self.tools.dispatch
        )

        # Append assistant message and tool results
        messages.append({
            "role": "assistant",
            "content": self._extract_content(message) or None,
            "tool_calls": [
                {
                    "id": tc.id,
                    "type": "function",
                    "function": {"name": tc.function.name, "arguments": tc.function.arguments},
                }
                for tc in message.tool_calls
            ],
        })
        for tr in tool_results:
            messages.append({
                "role": "tool",
                "tool_call_id": tr["tool_call_id"],
                "content": tr["result"],
            })

    return self._extract_content(message)
```

### 3.2 重构Swarm任务分配（P0）

**当前问题**：`_execute_plan()` 用 `exp in task["description"]` 做字符串匹配，经常失败。

**修复方案**：改为基于LLM的智能分配 + 白玉方法论的结构化分析流程：

```python
async def _analyze_and_plan(self, task: str) -> Dict:
    """基于白玉三维逻辑的结构化分析规划。"""
    # 1. LLM分析任务，决定需要哪些维度的分析
    analysis_prompt = f"""
    分析以下竞赛任务，按白玉"三维逻辑"决定需要哪些专家：

    任务：{task}

    可用专家角色：
    {self._format_roles()}

    请返回JSON：
    {{
        "analysis_dimensions": ["选题", "内容", "呈现"],
        "recommended_roles": ["role_id_1", "role_id_2"],
        "subtasks": [
            {{"description": "...", "role_id": "...", "dimension": "选题|内容|呈现"}}
        ]
    }}
    """
    plan = await self._llm_call_fn(
        [{"role": "user", "content": analysis_prompt}],
        tools=None
    )
    return self._parse_plan(plan)
```

### 3.3 引入"三维逻辑"分析流程

**建议新增**：在 Swarm 编排中引入白玉的三维逻辑作为结构化分析框架：

```
用户请求 → 三维逻辑分析
  ├── 第一维：选题诊断（竞赛选题战略家）
  │   ├── 国家战略匹配度
```
